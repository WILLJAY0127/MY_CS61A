核心主旨
原生嵌套列表虽然能表达层级，但是没有约束、结构杂乱，容易写乱；
树（tree）抽象就是给层级数据定一套统一规范 + 配套的构造 / 读取接口，不再裸着直接操作嵌套列表。
底层实现依然复用了列表的闭包属性（列表里可以放列表），但是上层通过 tree / label / branches / is_tree / is_leaf 建立抽象屏障。
✅ 上层代码禁止直接写 t[0]、t[1:]，统一用选择器 label(t)、branches(t)。
以后就算底层不再用列表存树，上层遍历、处理树的代码完全不用改动。
逐段梳理定义
树的递归定义（核心）
一棵树 = 根标签 (root_label) + 一组分支 (branches)
每一个分支本身仍然是树（递归）
没有分支的树 → 叶子 leaf
树里面嵌套的树 → 子树 subtree
所有子树的根，统称为节点 node
这套抽象的三个核心组件
构造器：tree(root_label, branches=[]) → 用来生成一棵合法的树
选择器：label(t) 取根标签；branches(t) 获取所有分支子树
校验工具：
is_tree(t) 判断是不是格式合法的树
is_leaf(t) 判断是不是叶子（没有分支）

运行
def tree(root_label, branches=[]):
    for branch in branches:
        assert is_tree(branch), 'branches must be trees'
    return [root_label] + list(branches)

入参：根标签，分支列表（默认空列表，就是叶子）
断言校验：每一个分支必须是合法树，不合法直接报错，保证构造出来的树一定格式良好
返回底层结构：[根标签, 分支1, 分支2,...]（分支本身也是列表，也就是子树）
python
运行
def label(tree):
    return tree[0]

def branches(tree):
    return tree[1:]

选择器！封装底层索引读取，抽象屏障的关键。
python
运行
def is_tree(tree):
    if type(tree) != list or len(tree) < 1:
        return False
    for branch in branches(tree):
        if not is_tree(branch):
            return False
    return True

递归校验：
首先必须是非空列表
每一个分支都必须是合法树
python
运行
def is_leaf(tree):
    return not branches(tree)

分支为空 → 叶子节点

plaintext

但是业务代码不要直接操作这个嵌套列表，必须走 label / branches。
为什么教材说 “嵌套列表会带来复杂度，树用来规整”
裸写嵌套列表的时候，没人强制结构：
有人写成 [1, [2,3]]，有人写成 (1, (2,3))，有人混入普通数字和列表，代码没法通用遍历。
树抽象强制统一范式：任何树都统一是 label + 子树序列，于是我们可以写出通用递归函数（统计节点、统计叶子、map_tree 等）。

✅ 一句话结论
在这个 CS61A 当前这套实现下：树底层就是一个符合固定格式的嵌套列表，是【规范化、受约束的嵌套列表】。
但是！从【抽象层面】来说：树 ≠ 嵌套列表。
这里要严格区分两层视角（CS61A 抽象屏障核心考点）
底层实现视角（现在这个版本）
tree() 构造出来的对象本质就是 list，格式强制固定：
plaintext
[label, 子树1, 子树2, ...]

并且通过 is_tree + assert 强制约束：每一个子元素要么不存在，要么也必须是同样格式的树（嵌套列表）。
👉 所以从物理存储上，它就是一套规范好结构的嵌套列表
数据抽象视角（最重要！）
树是一套抽象接口（构造器 tree + 选择器 label/branches），它只是恰好现在用嵌套列表来实现。
抽象的定义只关心：能不能拿到根标签、能不能拿到分支子树，不关心底层到底用什么存。
我们完全可以不改上层任何树处理代码，换别的底层存储：
比如不用 list，改用元组、或者自定义类、或者序对cons去实现 tree/label/branches。
上层的sum_tree、count_leaves、map_tree全部不用修改，依然正常运行。
👉 这就是抽象屏障：使用者不应该依赖 “它底层是列表” 这个事实，只使用规定的接口。
📌 一句话区分
裸嵌套列表：无规则，随便写 [1, [2, [3,4], 5], 6]，结构想怎么来就怎么来，没有强制规范，不一定能当成树。
本节的 tree：强制规范的嵌套列表，严格满足：
必须是非空列表
第一个元素是标签
后面所有元素全部也都是合法的树
没有多余乱七八糟的结构
❗ 容易踩坑的表述判断题（考试常考）
树是嵌套列表 → ❌（抽象层面不对，只是当前实现是嵌套列表）
在本节实现中，树由格式规范的嵌套列表表示 → ✅

✅ 核心一句话
列表、树，都不是自然界本来就有的东西；它们都是人「为了解决一类高频问题，人为发明出来的标准化数据模板」。
我们分开回答：列表是怎么来的 → 树是怎么来的
一、列表（sequence /list）是怎么来的？
很早很早，程序员就频繁遇到一类需求：需要存放一串有序的同类东西
比如：一堆成绩、一串字符、一系列待执行任务。
最原始的痛点：
变量是单个值 a=1，但我有 100 个数字，不可能手动写 100 个变量。
→ 需求：一个容器，能按顺序装一堆东西，可以按序号取出，可以遍历
于是人们提炼出这个抽象：序列（list）
契约非常简单：
能知道总长度 len
可以按下标取第 N 个元素 s[i]
后面又发现：列表支持闭包属性—— 列表里可以继续放列表，于是它不止能存一维线性数据，还能表达层级。
一句话总结列表的起源：
因为我们经常需要「有序的一串数据」，所以发明了列表这个抽象。
二、树（tree）是怎么来的？
人类同样有另一大类超级高频、但列表很难舒服表达的需求：层级、从属、分叉关系
举现实里天然就是树形的东西：
文件系统：根目录 → 文件夹 → 子文件夹 → 文件
组织架构：总经理 → 部门经理 → 员工
算术表达式：(1 + 2 * 3)，运算有优先级，天然分叉
分类、生物分类、家谱、决策分支、语法结构（编程语言语法树）
👉 这类关系有个共同特征：
有一个起点（根），分出若干子项；每个子项自己又可以继续分出子项。
它不是一条直线（所以一维列表不好表达）；
它没有循环、没有互相交叉（和图不一样）。
如果强行用裸嵌套列表去描述这种层级：
没有统一标准，每个人写法不一样，写通用遍历 / 计算函数非常麻烦。
于是人们单独提炼出一套专属抽象：树
契约：
每个单元有且仅有 1 个标签
附带若干分支，每个分支本身也是同规格的树
没有分支就是叶子
一句话总结树的起源：
因为大量现实问题天然是「单根分叉的层级结构」，裸嵌套结构不好统一处理，于是专门发明树这个抽象。
📌 关键对比（回答你最核心的好奇）
列表 → 为线性有序集合而生
树 → 为单根分叉的层级从属结构而生
补充：还有别的经典抽象，也是这么 “按需诞生” 的
集合 set：需要关心「存在与否，不关心顺序、去重」
字典 dict：需要「key→value 映射」
图 graph：需要任意节点互相连接（允许交叉、环）
🧠 一个更底层的视角（SICP/CS61A 的底层世界观）
计算机本身只有基础数字、布尔值这些原始数据。
所有复合数据抽象（序对、列表、树）全都是人凭空定义一套契约：
规定它支持什么操作（构造器、选择器），不规定底层怎么存。
只要契约满足，底层可以随便换实现：
树可以用嵌套列表实现
树可以用数组实现（堆就是数组形式的树）
树可以用对象 + 指针实现（Java/C 里最常见）
抽象的本质：不是发现了树 / 列表，而是我们约定一套规则，方便批量解决一类问题。
补充一个有意思的点：历史先后
最早计算机里先有数组（列表前身）；
随着编译器、语法解析、文件系统发展，大家发现层级结构到处都是，树才被提炼成标准数据结构。
SICP/CS61A 的编排顺序：
先教你基础复合数据（序对→列表），再利用列表的闭包能力，落地实现树这个抽象。
所以体感上会 “突然冒出树”，但从真实工程历史上：树是现实需求倒逼出来的独立抽象，不是列表的附属品。
