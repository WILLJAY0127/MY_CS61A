

创建模块化程序的一种有效方法是整合可能随时间改变状态的数据。  这句话为啥是整合可随时间改变状态的数据
原句
创建模块化程序的一种有效方法是整合可能随时间改变状态的数据。
An effective approach to creating modular programs is to bundle data whose state may change over time.
关键词：bundle（整合 / 打包）
不是把很多零散变量简单放一块，而是：把一组属于同一个事物、会一起变化的状态，封装成一个单元。
举反面例子（没整合状态，模块化很差）
假设我们模拟银行账户，分散写一堆独立全局变量：
python
运行
account_balance = 1000
account_owner = "Alice"

余额account_balance会随取款 / 存款变化。但状态是零散的全局变量。
任何函数都能随便修改account_balance，很容易改错、变量互相干扰。状态和业务逻辑分离。
整合之后（bundle，打包在一起）
把属于同一个账户的所有可变数据打包成一个单元（对象）
python
运行
class Account:
    def __init__(self, owner, balance):
        self.owner = owner
        self.balance = balance  # 可变状态
    
    def deposit(self, amount):
        self.balance += amount

owner、balance这一组属于账户的数据打包整合在一起，它们共同代表 “账户” 这个实体，余额会随时间变化。
为什么这句话要强调「可随时间改变状态的数据」
如果数据永远不变（不可变），打包的必要性没那么强。
常量、不变的描述，拆成零散变量问题不大。
一旦数据会变化（可变状态）：
状态之间有依赖（存款改变余额）
修改操作会改变历史，后续行为受之前操作影响
如果分散在全局，很容易出现状态不一致、脏数据、多处随意篡改。
→ 所以要把这一组耦合在一起、会变化的数据打包整合，作为独立单元。
和 CS61A 上下文串起来
前面章节：函数式、闭包、树、链表，偏向不可变抽象，构造新结构而不是修改旧数据。
到这里，正式切换视角：
现实实体自带持续变化的状态，为了模块化，把一组联动可变数据打包，这就是 OOP 的起点。
一句话浓缩：
一组会一起变动、属于同一个实体的数据，不要散放在程序各处，打包到一起，这就是整合可变状态数据。
如果你想，我可以对比：闭包实现状态 和 class 对象实现状态（CS61A 经典对比）。

中英对照
In the beginning of this text, we distinguished between functions and data: functions performed operations and data were operated upon. When we included function values among our data, we acknowledged that data too can have behavior. Functions could be manipulated as data, but could also be called to perform computation.
中文
在本文开头，我们区分了函数与数据：函数执行操作，而数据是被操作的对象。当我们将函数值纳入数据范畴时，我们承认了数据也可以具备行为。函数既可以像数据一样被处理，也可以被调用以执行计算。
CS61A 这段的核心含义（承接刚才 OOP 那一段）
1. 早期朴素划分（传统视角）
函数 = 动作、操作
数据 = 被动的东西，只能被函数读取 / 修改
👉 二者是完全分开两类东西。
2. 高阶函数打破这个边界（你前面一直在学的）
Python 里函数是一等公民 (first-class)：函数本身就是数据，可以赋值、传参、放进链表 / 树里。
函数可以当作数据被搬运（manipulated as data）；同时它仍然能被调用运行（()执行计算）。
这就引出关键结论：
✅ 数据不再只是静态数字、列表；数据里面可以携带行为（函数）
这是从「函数式抽象」过渡到「面向对象」的桥梁：
对象本质就是：状态数据 + 绑定在这个数据上的行为（函数 / 方法）
3. 和上一段落串联起来
上一句：把一组可变状态打包在一起（OOP 起点）
这一句：我们已经有能力把行为（函数）也放进数据里
两者合并，就构成对象：
对象 = 可变状态数据 + 依附于该数据的行为函数
极简例子（直观感受）
python
运行
# 函数作为数据，存入字典（原始“对象雏形”，还没用class）
def deposit(acc, amt):
    acc["balance"] += amt

account = {
    "balance": 1000,    # 状态数据
    "deposit": deposit  # 行为：函数作为数据存进去
}
account["deposit"](account, 200)
print(account["balance"])
这里account这个数据容器，里面不仅有余额，还装了操作它的函数，也就是数据自带行为。
后面的 Class 只是把这个模式封装得更干净的语法糖。

拆两句分开讲，结合 CS61A 这个句子：
The logic of how an object interacts with other objects is bundled along with the information that encodes the object's value.
对象与其他对象交互的逻辑，和编码对象值的信息捆绑在一起。
When an object is printed, it knows how to spell itself out in text.
打印对象时，对象知道如何用文本描述自己。
第一句：对象和别的对象交互逻辑，跟自身数据打包在一起
❌ 旧方式（函数、数据分离）
数据是单独的字典a，交互函数transfer写在外面。转账逻辑不属于账户本身，是外部全局函数。
python
运行
# 两个账户（单纯数据）
a = {"name":"A", "balance":100}
b = {"name":"B", "balance":200}
# 交互逻辑在外面，不属于a、b
def transfer(from_acc, to_acc, amt):
    from_acc["balance"] -= amt
    to_acc["balance"] += amt
transfer(a,b,50)
👉 问题：transfer是游离在数据之外的逻辑。账户本身不知道 “怎么转账”，全靠外部函数操作它。
✅ OOP 方式（打包在一起）
把账户数据 + 和别的账户交互的逻辑（转账） 全部放进 Account 类，变成对象自带方法：
python
运行
class Account:
    def __init__(self, name, balance):
        self.name = name
        self.balance = balance
    # 交互逻辑：和另一个Account对象转账
    def transfer(self, other_account, amt):
        self.balance -= amt
        other_account.balance += amt

a = Account("A",100)
b = Account("B",200)
# 交互逻辑属于a这个对象，直接调用
a.transfer(b, 50)
self.name / self.balance：编码对象值的信息（状态数据）
.transfer()：和其他对象交互的逻辑
两者打包在同一个对象单元内，这就是这句话的含义。
第二句：打印对象时，对象知道如何用文本描述自己
还是上面这个 Account 例子。
如果不定义__repr__，直接 print 对象，Python 会输出默认的内存地址：
python
运行
print(a)
# <__main__.Account object at 0x7f882345>
这串东西没意义，对象不知道怎么描述自己。
我们把描述自身的逻辑写进对象内部（__repr__）：
python
运行
class Account:
    def __init__(self, name, balance):
        self.name = name
        self.balance = balance
    def transfer(self, other_account, amt):
        self.balance -= amt
    # 【对象自带描述自己的逻辑】
    def __repr__(self):
        return f"Account(name={self.name}, balance={self.balance})"

a = Account("A",100)
print(a)
# Account(name=A, balance=100)
现在，打印这个对象的行为规则，写在对象内部。不是外部单独写一个format_account()函数去把账户转字符串。
当你调用print(a)，Python 会自动触发对象内部的这个方法 —— 也就是原文说的：对象知道怎么把自己写成文本。
一句话总结两段
交互逻辑（比如转账）不再是外部独立函数，而是属于对象本身，和对象的数据打包在一起；
“怎么把自己变成文字” 这个规则，也放在对象内部，不是外部单独写格式化代码。
底层本质：方法就是绑定在实例上的函数，属于对象的一部分，而不是游离在外。
