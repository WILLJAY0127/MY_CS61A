分模块说：为什么按这个顺序安排这些内容
1. 先上 list（可变序列）+ 扑克牌案例
前面章节的代码都是无副作用：表达式求值只会产出新值，不会偷偷改别的变量。
但真实程序里大量可变数据，会出现你没写这个变量，它的值却变了（也就是 chinese 明明没操作，跟着 suits 一起变）。
扑克牌故事只是包装，载体是一系列列表原地操作：pop / remove / append / extend / 切片赋值
真正要抛出的新现象：别名（多个名字绑定同一个可变对象）带来隐性副作用
这是学生第一次接触「引用共享」，是思维转折点。以前写代码直觉：不碰变量，变量就不变；从这里开始这个直觉失效。
2. 紧接着：浅拷贝 + 嵌套列表 nest 例子
光知道 “别名会同变” 不够，还要区分完全共享和部分共享（浅拷贝）：
python
运行
nest = list(suits)   # 外层新列表
nest[0] = suits      # 但第一项又指向旧列表，局部别名

这里要传递关键认知：
复制不等于完全隔离，共享结构才会互相影响，不是只要复制就万事大吉。
这个点是后面工程 bug 高频来源，也铺垫之后深拷贝的概念。
3. 引出 is 和 ==：区分【身份相同】和【值相等】
光靠肉眼看内容分不清两个列表是不是同一个对象：
两个列表字面内容一模一样，但可能是两个独立对象；
两个名字指向同一个对象，改一个全部变化。
==：值相等，只比对里面元素
is：同一个对象（身份一致），强条件，直接决定会不会互相影响
这是一套判断工具，以后遇到任何共享问题，都能用 is 排查。
4. 列表推导式
专门强调：列表推导式永远生成全新列表，不会复用原有列表对象
刚好和前面 “原地修改、共享引用” 做对照：同样产出序列，一种是修改老对象，一种直接新建对象。
顺带用 unicodedata 扑克牌花色做可视化小例子，趣味性同时巩固。
5. 最后引入 tuple（不可变序列）
序列有两大类：可变 (list) / 不可变 (tuple)，补齐序列的完整分类。
重点的难点一句话：
元组本身不可变 ≠ 元组里面装的可变元素不能改
python
运行
nest = (10, 20, [30, 40])
nest[2].pop()  # 合法！

这个是必考坑点：
元组约束的是元组这个容器本身不能换里面的元素引用，但如果元素是列表这种可变对象，列表内部依然可以原地修改。
收尾再提多重赋值隐式用元组，为之后函数多返回值、解包做铺垫。
整体串联：这一节想给你建立的完整认知链条
序列分为可变（list）、不可变（tuple）两类
可变对象支持原地修改 → 会产生别名共享副作用（全新的编程现象）
怎么判断是不是同一个对象？is；怎么判断内容一样？==
拷贝有深浅之分，只有存在共享结构才会互相影响
元组虽然不可变，但里面如果嵌套可变对象，依然存在副作用

分开两层理解：
1. 为什么本节正文很少直接写 “抽象、组合”？
抽象和组合是全书顶层目标，不是每一小节都要反复复述的关键词。
之前讲序对、序列、高阶函数：直接展示怎么组装、怎么隔离细节（抽象屏障）
本节的任务不是教你怎么设计抽象 / 怎么组合，而是告诉你一个残酷事实：
只要你的数据是可变的，组合出来的系统会出现之前不存在的隐性副作用，这件事会直接击穿抽象屏障！
举个例子（和扑克牌案例对应）：
如果我把 suits 这个列表传给好几个不同的函数（组件组合）。
在不可变世界：每个函数读取 / 计算，互不干扰，抽象边界很清晰。
在可变世界：其中一个组件原地修改了列表，别的完全无关的组件会偷偷拿到变化后的数据。
👉 抽象直接失效！模块之间出现了看不见的隐式耦合。
本节所有例子，都是在展示这个风险的底层来源：别名 + 可变对象共享
扑克牌 chinese /suits：别名共享，改一个另一个跟着变
nest 嵌套浅拷贝：局部共享，不是全共享，坑更隐蔽
is vs ==：给你工具，用来识别 “是不是共享同一个可变对象”
tuple 内含列表：更隐蔽的共享陷阱（容器不可变，但内部可变）
列表推导式：一种安全的组合方式（直接新建列表，不共享）
2. 这一节真正在为【抽象、组合】解决什么前置问题？
等后面要你做带状态的抽象（比如做一个卡牌游戏、数据容器）的时候，你必须先懂：
什么时候两个组件共享同一份数据
修改会不会波及别的组件（会不会打破抽象隔离）
哪些操作会新建对象、哪些是原地修改（组合的时候选哪种）
如果跳过本节直接去学 “可变数据抽象”，你根本理解不了：
为什么有时候要拷贝数据？
为什么封装状态的时候要防止外部拿到内部可变引用？
这些软件工程里抽象屏障的核心要求，根源全是本节讲的别名与可变性。
