## 📖 开篇定义 + 最简测试代码（词法作用域 = 看代码写在哪，不看代码在哪跑）

### 教材原文核心两句话
> 局部定义的函数也可以访问其定义所在作用域中的命名绑定。关键在于，内部函数可以访问其定义所在环境中的名称（而非调用它们的环境中的名称）。

### 1. 什么叫「定义所在环境」（看这里）

```python
def sqrt(a):          # a 属于 sqrt 的局部作用域
    def update(x):    # update 的【源代码文本】写在这里
        return average(x, a/x)
    return improve(update, close)
```

👉 **定义所在环境 = 写 `def update` 那一行时，周围包裹的外层局部帧（sqrt 调用产生的那套局部环境）**。
所以 update 找 `a` 永远回 sqrt 的局部帧拿，哪怕以后 update 被作为返回值、传到 improve 内部、跑到程序任何别的角落被调用——找谁拿 `a` 这件事，在 `def update` 写下去那一刻就定死了，和调用现场**完全无关**。

### 2. 什么叫「调用它们的环境」（别往这看，忽略）

```python
def f():
    b = 100
    my_update(5)   # 这里是【调用现场】，调用者是 f
    # my_update 不会来这里找 a 和 b！！

u = make_update(2, 3)
my_update = u
```

my_update 是写在 `make_update` 里面的，不是写在 `f` 里面的。
哪怕在 `f()` 里面调用 `my_update(5)`，它**不会**去 f 的局部作用域找 a、b，依旧回当初 `make_update(2,3)` 创建时那套老环境拿 a=2, b=3。

✅ **词法作用域（Python/JS/Scheme 都是这套）：看源代码文本写在哪**
❌ **动态作用域（只有 bash 等老脚本用）：看谁调用我**

### 3. 最直观演示代码（必记输出）

```python
def outer(x):
    def inner():
        print(x)
    return inner

f1 = outer(10)     # f1 绑定的是 outer(10) 这套环境，记住 x=10
f2 = outer(20)     # f2 绑定 outer(20)，记住 x=20

def caller(x):     # 这里的 caller(x=999) 和 f1 查找变量完全无关
    f1()

caller(999)
```

**输出是 10，不是 999。**
f1 定义时绑定 outer(10) 那一份环境，虽然在 caller(x=999) 里面被调用，但调用者的局部变量 x=999 根本不参与查找。这就是词法作用域最朴素、最直接的证明。

## 一、为什么突然冒这个破名词？闭包 vs 词法作用域的边界（别混）

很多人读到这里晕：前面一直在聊「父函数 return 了内层还能读 a」的闭包现象，现在突然抛新词「词法作用域」——**两件事不要混在一起，它们是因果关系不是同义词**。

| 维度 | 词法作用域 Lexical Scope | 闭包 Closure |
|------|--------------------------|--------------|
| 性质 | **静态源代码层面的规则**（看文本写在哪）| **运行时产生的实体/现象**（内存里的东西）|
| 回答的问题 | 「我要找一个变量 a，去哪里找？这套查找规则叫什么名字？」| 「父函数早就 return 退出了，为什么它的局部帧还活着没被GC回收？」|
| 发生时机 | 写 `def` 那一瞬间就定死了查找链路，程序还没跑就已经存在 | 程序跑起来、内层函数对象**逃逸**（被return/存到外部变量）之后才产生 |
| 61A 画图体现 | 函数对象的 `enclosing environment` parent 箭头指向谁 | 本来该销毁的父帧，因为被内层函数对象持有引用，GC 不回收 |

> 🧠 一句话极简区分：**词法作用域是「为什么能找到变量」的规则；闭包是这套规则跑起来之后，内存里保留下来的东西。**

### 交通法规小类比
- 交通法规 = 词法作用域：一套写在书本上的静态规则，先有法规才有后面的实物
- 路上跑的汽车 = 闭包：严格遵守法规才会出现的运行时实物
- 法规≠汽车，但**没有法规就造不出能合法上路的车**
- 同理：**没有词法作用域这套查找规则，就产生不出闭包现象**

### 反面验证：如果不是词法作用域（动态作用域），就造不出闭包

```python
def sqrt(a):
    def update(x):
        return average(x, a/x)
    return improve(update, close)
```

如果 Python 是动态作用域：`update` 找 `a` 会去**当前调用它的 improve 的局部环境**找，improve 里没有 a → 直接报错。
正因为 Python 是词法作用域，`update` 找 `a` 永远回写 `def update` 那一刻的 sqrt 局部帧——**规则先存在，才有后面的内层能读 a / 帧被续命的闭包现象**。

### 61A 学习链条正确顺序（别搞反）
```
遇到问题：sqrt_update(x,a)双参和improve不兼容
   ↓
解决方案：嵌套def，造出只带x的update
   ↓
观察现象：update居然能读父帧的a，哪怕sqrt return了
   ↓
📌抛出名词：这套查找规则=词法作用域（静态文本决定查找链）
   ↓
运行时产物：遵守词法作用域 → 内层函数带parent指针逃逸 → 形成闭包
```

## 二、「词法」这破名字的历史由来（为什么不直接叫「文本嵌套作用域」）

完全同意：从理解角度「文本嵌套作用域」比「词法作用域」友好一万倍。但学术圈用 lexical scope 有**历史原因 + 精准度原因**两层：

### 1. 历史原因：来自 50-60 年代 Lisp 研究的专业术语
61A 的血脉就是 Scheme/Lisp，lexical scope 这个术语在那个年代就定型了，后世语言 Python、JS 全部沿用，属于行业标准历史遗留——不是故意起晦涩名词为难人。

### 2. 精准度原因：「文本嵌套」只是最常见的现象，概括不了完整规则
「嵌套」描述的是你肉眼看到的缩进/def层级，但「词法作用域」强调的是更核心的事实：
> **每个标识符的所属环境，完全由源码文本位置静态决定；无论这个函数将来被传递到程序的哪个角落被调用，查找规则永远不变。**

光说「嵌套」会漏掉后半句——看反例就懂：

```python
def outer(x):
    def inner():
        print(x)
    return inner

f = outer(100)

def outer2(x):
    f()          # 调用发生在 outer2 内部

outer2(999)
```

肉眼看：`f(=inner)` 的源代码写在 `outer` 里，**不是写在 `outer2` 里**——所以虽然调用现场文本缩进在 outer2 里，但 inner 的查找链根本不沾 outer2 的 x=999，输出还是100。
这里的核心重点不只是「嵌套在哪个大括号/def里」，而是「**绑定定义处的环境，跟调用现场完全无关**」——所以教科书不用「嵌套作用域」当正式名词，用词法作用域(lexical)强调静态、不依赖运行时。

### 自用翻译方案（考试写学名，脑子这么翻）
- 写作业/考试/画图：照规矩写「词法作用域 / lexical scope」
- 自己思考/排查bug时：**🧠 自动替换成「源码文本位置决定的作用域」→ 再短一点 = 「看代码写在哪，不看代码在哪跑」**

## 三、教材原文拆解：词法作用域的两大核心优势

> Hence, we realize two key advantages of lexical scoping in Python.

### 优势 1：命名隔离（不污染全局命名空间）

> The names of a local function do not interfere with names external to the function in which it is defined, because the local function name will be bound in the current local environment in which it was defined, rather than the global environment.

翻译人话：嵌套内部起的函数名字，只存在外层函数的**局部帧**里，不会跑到全局帧。

```python
def sqrt(a):
    def sqrt_update(x):   # sqrt_update 这个名字，只存在 sqrt 的局部帧
        return average(x, a/x)
    ...
```

- `sqrt_update` 不是全局名字
- 你在另一个函数 `newton(a)` 里面照样可以再定义一个同名 `sqrt_update`，**两套局部帧互不打架**
- ✅ 解决的真实问题：全局名字不会泛滥，不会到处重名冲突
- 反过来说：**如果没有词法作用域**，嵌套def出来的名字会直接漏到全局，写一个大工程根本没法协作

### 优势 2：内层函数可以访问外层包裹函数的环境

> A local function can access the environment of the enclosing function, because the body of the local function is evaluated in an environment that extends the evaluation environment in which it was defined.

这句话直接对应 61A 环境模型的**两条铁律**（和 1.6.3.md 的 parent 规则完全一致）：

| 时机 | 发生了什么 | 对应词法作用域 |
|------|-----------|----------------|
| 🕒 函数**定义**时刻 | 函数对象内部记一个 `parent = 当前外层环境`（比如 sqrt 的局部帧）| parent是谁 = 看写def时的外层环境 = 词法 |
| 🕒 函数**调用**时刻 | 新建调用帧，新帧的父环境**直接复制**函数对象存好的 parent（不看调用者！）| 继承的是【定义时】的环境，不是【调用时】的现场 |

执行函数体找变量：沿着这条链（自己局部绑定 → 继承来的 parent → parent.parent ... → global）往上搜索。
**这就是为什么就算外层函数已经 return，只要函数对象还持有那个旧环境引用，依然能读到旧变量。**

## 四、一句话吃透第二句长难句 + Java lambda 对比

### 长难句精准翻译
> local function is evaluated in an environment that extends the evaluation environment in which it was defined.

🧠 **一句话吃透：执行内层函数的时候，会新建一个调用帧；这个帧的环境链，是在「函数当初定义时的环境」基础上扩展，不是在「调用现场的环境」基础上扩展。**

- 扩展自【定义时环境】= 词法作用域（Python 真实行为）
- 扩展自【调用现场环境】= 动态作用域（Python 不用这套）

### Python 词法作用域 vs Java lambda 实现路径（本质不一样）

| 维度 | Python（词法作用域 + 环境链模型）| Java（匿名类 / lambda 捕获）|
|------|---------------------------------|----------------------------|
| 实现机制 | 运行时解释器维护完整帧链，函数对象持有外层帧的引用 | 编译期把捕获的变量**复制为匿名类的隐藏字段** |
| 查找行为 | 运行时沿着 parent 帧链动态 lookup 名字 | 直接读类字段，不存在运行时帧链查找这回事 |
| final限制 | 没有 final 语法限制（用 nonlocal 声明就可以改）| 捕获的变量必须是 effectively final（编译期强制检查）|
| 61A考察 | 画环境图，箭头指向定义时的帧 | 61A 不考 Java，只是业务效果类似 |

> ⚠️ 业务上 Java lambda 也能做到「好像读了外层变量」，但底层完全不是词法作用域这套运行时 parent 环境链模型——它是编译期就把值拷贝进对象里了，是**扁平的字段拷贝模型**不是**长链的帧继承模型**。

## 五、🔥 Top1 极混卡点：调用链 = 动态作用域吗？（90% 人第一反应混淆）

答案先给死：**调用链 ≠ 动态作用域。** 两者是完全不同的东西，只是动态作用域刚好「借用了调用链」当查找链路。

### 先划清两件事的边界
| 名词 | 本质 | 哪些语言有 | 和作用域规则的关系 |
|------|------|-----------|-------------------|
| **调用链 / 调用栈 (call-stack)** | 物理运行时栈，记录「谁调用了谁」的执行历史，异常栈回溯就是打印这个 | 所有语言都有（Python/Java/C/JS全有）| 它只是硬件/解释器的通用机制，本身不是作用域策略 |
| **动态作用域 (dynamic scoping)** | 一套**名字查找规则**：找变量的时候，顺着调用链（调用栈）往上搜调用者的绑定 | 只有老脚本用（bash等），Python/Java/JS全不用 | 是一套作用域策略，刚好使用调用链做查找链路 |

### 两套查找链终极区分
```
词法作用域（Python 真实行为）：
查找链 = 【定义时的静态文本嵌套链】→ 函数对象预先存好的 parent 环境链
         跟调用栈是谁、调用者有什么局部变量 → 完全无关

动态作用域（Python 不用，仅假想）：
查找链 = 【运行时的调用链（调用栈）】→ 顺着栈往上看调用者帧里有什么绑定
         跟函数在哪写的、parent指谁 → 完全无关
```

### 反例戳穿幻觉：栈上明明有帧，inner 完全看不见 caller 的局部变量

```python
def outer(a):
    def inner():
        print(a)
    return inner

def caller(b):
    fn = outer(100)
    fn()   # 调用 fn 的时候，caller 在调用栈上，有局部变量 b=20

caller(20)
```

此时的运行时画面：
- 📚 **物理调用栈**：`caller` → `fn(=inner)`（没错，caller 真的在栈上，帧里有 `b=20`）
- 🔍 **Python 实际变量查找链**：`inner 自己的帧` → `outer(a=100) 的帧` → `global`（完全不经过 caller）
- inner 根本读不到 caller 的 `b=20`，**哪怕 caller 的帧明明白白躺在调用栈上**

这就是 61A 要教你最核心的反直觉点：**Python 有调用栈，但是它找变量完全抛弃调用栈，改用函数对象定义时就绑定好的 parent 环境链（词法链）**。

## 六、词法作用域 vs 动态作用域终极对比（一张表记完）

| 维度 | 词法作用域（Lexical / Python/JS/Scheme 真实行为）| 动态作用域（Dynamic / bash 老脚本假想）|
|------|-------------------------------------------------|--------------------------------------|
| 查找变量看 | 源代码文本写在哪（def 写下去那一刻的外层环境）| 谁在调用我（运行时的调用栈）|
| 查找链路 | parent 静态文本嵌套链（定义时就定死，永远不变）| 运行时调用链（每次调用链不一样结果就不一样）|
| 闭包现象 | 能产生闭包（帧被内层带走续命）| 产生不了闭包（调用完就散，没有独立的 parent 链）|
| 代码可预测性 | 高——看代码文本就能确定去哪里找变量 | 低——必须知道调用上下文才能推演 |
| 61A画图体现 | 函数对象enclosing箭头→定义时外层帧 | （61A不考，仅做对比用）|
| 演示例子输出1：`g = f(10); g()` 全局x=200 | **输出10**（取定义g时f的局部x=10，无视全局x后来变成200）| 输出200（取调用现场的全局x=200）|
| 演示例子输出2：`h(20)` 里面调 `f(100)` 返回的g | **输出100**（g的parent是f帧，和h调用者无关）| 输出20（顺着调用栈找，拿h的x=20）|

### 🧠 记忆口诀（背下来不丢分）
- **动态作用域：顺着调用栈往上找 → 「谁调用我，我看谁」**
- **词法作用域：顺着定义时文本嵌套链往上找 → 「我在哪写的，我回哪」**
